# Ahl El Kheir Internationalization (AR / EN)

Arabic is the default language and English is the alternate language.

## Architecture

The project uses **stable key-based i18n**. New UI code must never use an Arabic sentence as a translation identifier.

- `config/lang.php` resolves the active language and provides `t()` / `ak_t()` plus the shared client dictionary.
- `lang/ar.php` is the authoritative Arabic key catalog.
- `lang/en.php` is the authoritative English key catalog. Both catalogs must contain the same keys.
- Module catalogs under `lang/*_ar.php` and `lang/*_en.php` extend the same stable catalog and are loaded automatically.
- `lang/legacy_en.php` is a temporary Arabic-to-English compatibility bridge for pages still awaiting source migration. It is not a catalog for new work.
- `assets/js/language.js` provides `AKLang.t()` for dynamic client-side UI and a **safe exact-match compatibility pass** for dynamically inserted UI text/attributes.
- `tools/i18n_audit.php` validates catalog parity and reports hard-coded Arabic UI literals and unknown key usages.

## New code

PHP:

```php
echo t('families.add');
echo t('families.total', ['count' => $total]);
```

JavaScript:

```javascript
AKLang.t('messages.send');
```

Use stable namespaces such as `common.*`, `families.*`, `orphans.*`, `sponsors.*`, `sponsorships.*`, `supervisors.*`, `messages.*`, `accounting.*`, `projects.*`, and `reports.*`.

## Dynamic values

Never translate a rendered sentence containing business values. Put placeholders in the catalog and interpolate after language selection:

```php
echo t('families.total', ['count' => $total]);
```

Example catalog value:

```text
families.total = Total Families: :count
```

## Data rule

**Never translate database data.** Names, addresses, notes, phone numbers, case information, sponsor information, document names, and other stored business data remain exactly as stored. Only application UI belongs in translation catalogs.

## Legacy migration

The old Arabic-to-English dictionary was moved to `lang/legacy_en.php` so it cannot be confused with the new authoritative English catalog. Existing pages may continue to work through the temporary exact-match compatibility layer while they are migrated.

The compatibility layer now has two safe stages:

1. Server-side exact-match translation of rendered UI text/attributes.
2. Client-side exact-match translation for UI inserted after page load.

Both stages only translate exact strings present in the loaded application dictionary. They do **not** translate substrings, arbitrary text, form values, database records, or user-entered content.

No new entries should be added to the legacy bridge. Every newly created UI term gets a stable key in both language catalogs and is rendered through `t()` or `AKLang.t()`.

## Language switching

The selected language is stored in the `ak_lang` cookie. Language switching is centralized and query parameters are normalized so repeated switches do not accumulate duplicate `lang` parameters. Arabic uses RTL and English uses LTR.

## Audit

From the project root run:

```text
php tools/i18n_audit.php
```

The audit checks that the authoritative catalogs have identical keys, detects unknown key usages, and lists Arabic source literals that require review. Arabic names/data are expected to appear in the review list and are not automatically changed.

## Completion rule

A page is fully source-migrated when its application UI no longer depends on `legacy_en.php` for English rendering. Until that final source cleanup is complete, the exact-match compatibility layer provides global coverage without translating business data. The compatibility layer is therefore a migration safety net, not the preferred mechanism for new development.

## Compatibility bridges and the gap report — 2026-09-21

`lang/bridge/` holds compatibility dictionaries. They are **not** stable-key catalogs and are never loaded by the `lang/*_ar.php` / `*_en.php` glob.

- `ar_to_en.php` — Arabic text of pages not yet migrated to `t()`. Server-side only (not sent to the browser). Lowest priority: `legacy_en.php` and the stable catalogs always win.
- `ar_to_en_js.php` — Arabic text produced by JavaScript and by native `confirm()/alert()/prompt()` dialogs. Small; sent to the browser through `ak_dict()`.
- `en_to_ar.php` — English text for the Arabic UI, scoped per page (script basename) so English words in stored data elsewhere are never replaced. `'*'` applies to every page.

Keys are the text **without** leading/trailing punctuation. `ak_core_lookup()` (PHP) and `translateByCore()` (`language.js`) re-attach that punctuation, so one entry covers `الاسم`, `الاسم *`, `الاسم:` and `هل أنت متأكد؟`.

Find what is still untranslated (CLI, project root):

```text
php tools/i18n_gap.php          # summary
php tools/i18n_gap.php --all    # every string
```

The report also lists some non-UI text (code fragments, single Arabic letters); ignore those. Text containing live values (counts, names, dates) cannot be handled by any dictionary — migrate it to `t('key', ['count' => $n])`.
